# 设计与模型选择

## 已修正：相邻肘部漏检与示例动作

v1 示例使用负的 `joint3`，上臂与前臂的原始 STL 在关节连接区域之外发生躯体交叉。
此前 `self_collision_ignore` 排除整个 `link2/link3` 对，使 GPU 和独立 CPU 球检查同时漏掉它。
独立实现 FK 一致只能证明坐标计算一致，不能证明碰撞排除配置正确。

原始 URDF 的 `joint3` 带 `rpy=-3.1416 0 0`，这是模型坐标定义，不应通过删除该变换或
翻转轴来掩盖反向折叠。v2 保留源模型，在两个物理 link 上添加固定的碰撞球别名；
取距离关节壳体邻域之外的原球作为额外躯体检查对。它们也进入 GPU 优化约束，
而非只在绘图时改姿态。别名无网格、无新增自由度、质量和惯量为零。

50 mm 壳体邻域来自当前 STL 审查，是离线几何近似：所核查正向姿态的真实非共面交点
位于肘轴约 35.6 mm 内，旧起点的交点延伸到约 99.5 mm，旧目标约 163.2 mm。
STL 不是闭合体，库返回的接触代表点也不一定是真实交点；这里使用相交三角形边的实际交点定位，
不把库的球重叠值或接触位置当成真实实体穿透深度。
额外球组是部分覆盖的躯体保护，不构成所有相邻关节结构的完整几何认证。

v2 起终点固定底座角，令 `q3+q4=0.1 rad`，通过肘、腕配合产生侧向接近。
旧运动的约 96.5° 腕端朝向变化主要来自选定的关节目标，不是优化器必须产生的大旋转。
`plan_cspace` 没有接收物体、抓取方向、TCP 或直线接近约束；它不能自行推断这些任务要求。
现在记录实际 FK 的位移、朝向漂移、路径长度与直线偏差，便于区分任务设定和求解结果。

若以后需要抓取末段，仍须定义夹爪 TCP、物体/预抓取位姿和接近方向，再建立并验证姿态及
路径约束。即使关节插值恰好保持末端朝向，末端位置也不必沿直线运动。

## 数据流和阶段边界

规划端按 `joint1` 到 `joint6` 接收 rad 关节角，加载 R5a 网格与派生 URDF，通过 `MotionPlanner.plan_cspace` 生成指定关节目标的轨迹。GPU 内部约束检查之后，CPU 重新检查数值、差分连续性和球体碰撞，才写入 JSON。控制端依据自己的模块文件哈希、配置和几何再次验证，然后进行 Mock 调度并记录目标与反馈。

真机端未来需要把已验证的实际关节状态带回规划端。直接 CLI 位置输入标为 `offline_test`；
按显式标定导入的已有反馈记录可绑定为 `hardware_snapshot_unverified`，仍不等于已验收的实时状态。
实际状态与计划起点不符时必须重新规划，不允许先跳到第一个点。

Python SDK 比 ROS2 更适合本项目的文件交换最小链路：可避免 ROS2 节点和消息层，已有六轴位置和七维反馈接口。但 SDK 底层时序、初始化动作、错误状态与停止确认未得到充分说明，因此目前保留接口契约与阻塞检查，**没有实现可解除的硬件执行开关**。改变 JSON 的资格标志或传入授权参数也不会构造 SDK。Mock 成功不会进入真实模式。

## 为什么 UR10e 示例看起来更简单

现有 `study/ur10e/motion_planning_ur10e.py` 加载的是 cuRobo 已提供的 `ur10e.yml`。
该文件已经包括基座、工具坐标系、关节顺序、默认姿态、速度之外的运动参数、碰撞球和排除表。
因此示例中的几行修改是在复用已经完成的机器人适配，而不是只替换一份裸 URDF。

URDF 提供关节树、变换、轴、网格以及部分关节限值；cuRobo 的碰撞球、关节空间配置和任务参数
仍需另外提供。R5 还包含两个夹爪关节，以及官方两份模型不完全一致的问题，增加了一次性配置工作。
本项目采用的细密自动包络球也增加了配置量和 CPU 复核耗时，这不是 R5 机械臂本身必然更复杂。

如果只比较离线模型显示和规划，R5 配置完成后同样可以是很短的示例。
`planning.demo` 现在按 UR10e 学习代码的顺序显式调用规划器、提取轨迹、初始化同款
`ViserVisualizer` 并逐帧调用 `set_joint_state`；代码直接显示每一步，不再把回放入口封装在
`view()` 中。关节空间目标仍用 `plan_cspace`，没有改成原 UR10e 示例的笛卡尔 `plan_pose`。
跨机状态、标定、SDK 时序、异常停止和部署预检来自最终真机目标；UR10e 学习示例没有完成这些任务。
这些功能与日常离线演示的操作入口独立，不需要为了查看运动先完成真机验收。

## 为什么选择 R5a 做离线模型

`ARX_Model/R5/R5a` 包含九个 link 的网格与两个夹爪滑动关节。SDK 的 `R5_master.urdf` 只提供六轴链，腕部原点、质量和质心也不同。不能把 SDK 关节原点与 R5a 网格拼成一个未经证实的新模型。当前保留 R5a 自身的完整变换链和网格，同时提供差异报告；两者对应什么硬件版本，公开文件未解释。

派生 URDF 仅调整资源路径、六轴位置范围及离线速度上限，没有修改原点、旋转轴、惯量或网格。位置范围取自官方 R5 ROS2 手册，但该范围与当前 R5a 模型及用户硬件零位的关系尚未实测。速度 0.4 rad/s、加速度 0.8 rad/s²、jerk 10 rad/s³ 是离线算法实验参数，没有被称为厂家安全上限。

base 为 `base_link`，规划末端为 `link6`，它是腕端模型坐标系，不是经标定的夹爪 TCP。夹爪 `joint7`、`joint8` 是分别沿 +Y、−Y 的 prismatic 关节，原始模型没有 mimic 关系。离线选择两者均为 0.044 m 的固定状态，保存两片夹爪几何。该值是 URDF 上界，既不是 SDK 的 0–5 夹爪命令，也不是测量的开口宽度。更换夹爪状态必须重建配置、复核碰撞并重新规划。

## 碰撞球的坐标与覆盖

每个 collision mesh 的缩放与 `collision/origin` 先变换到所属 link 坐标。算法在 PCA 坐标中递归裁剪三角面片，把各片多边形包在球内，再把球心旋回 link 局部坐标。球半径附加 1 mm 离线几何缓冲。基座、关键腕部和手指使用更细的球，以减少保守包络之间的假碰撞。实现按整个面片裁剪，不是仅挑选几个网格顶点。

运行时世界球心为 `base_T_link × [center_link, 1]`，半径不变。独立 CPU 验证器和 Viser 都用同一 link 局部定义；GPU FK 则独立加载相同 URDF。网格与球体图用于确认整体位置关系。

原始球组仍排除同一 link 和直接父子关节副；v2 额外加入 `link2_elbow_body` 与
`link3_elbow_body`，只让这两组别名相互检查，补上肘部躯体干涉。
**基座/link2、腕部非相邻 link 和两片夹爪之间仍进行检查。**
其他相邻结构及壳体邻域的排除仍是近似，不是整个工作范围内无干涉的证明。

模型包含 URDF 基座，但不包含实物安装板、G 型夹、桌面、线缆、载荷或其他环境。球覆盖的是源网格面片包络；没有完成真实结构测量或体积包含关系的完整证明。所有这些因素均阻止真机资格授予。

## 为什么仍进行独立轨迹验证

`result.success` 并不替代明确的终点误差检查和实机限制审查。导出器验证位置、速度、加速度及其有限差分，防止以全零速度字段掩盖位置跳跃。碰撞检查在线性关节段中加密到最大单轴步进 0.005 rad；这属于离散采样验证，不能证明控制器使用其他插值方式时的连续无碰撞。

当前 cuRobo 插值结果包括两个锁定夹爪关节。适配器先核对它们的位置和导数，然后根据关节名提取主动六轴。插值周期从 `planner.trajopt_solver.config.interpolation_dt` 获取；优化步长单独记录。25 ms 是文件采样周期，不是经确认的 SDK 控制周期。

Mock 的默认虚拟时钟使测试可重复，`--realtime` 用单调时钟的绝对截止时间模拟调度。状态新鲜度、起点误差、跟踪误差和最终静止检查均有失败路径。Mock 是瞬时精确跟踪模型，因此零跟踪误差只说明软件数据传递一致，不代表电机跟踪性能。
